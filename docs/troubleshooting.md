# 트러블슈팅 보고서

> 작성 근거: 2026-11-20 AWS 콘솔 및 Mac 터미널 실습에서 관찰된 결과. 관찰하지 않은 장애나 로그 분석 결과는 만들어내지 않았다.

## 사례 1 — 서브넷 CIDR 중복 오류

| 단계 | 내용 |
|---|---|
| 증상 | 이미 생성된 서브넷과 동일한 `10.0.1.0/24`로 두 번째 서브넷을 생성하려 하자 콘솔에서 `CIDR 주소가 기존 서브넷 CIDR: 10.0.1.0/24과(와) 중첩됩니다` 오류 표시 |
| 가설 | 동일한 VPC 내에 해당 IP 범위를 사용하는 서브넷이 존재하여 범위가 겹침 |
| 검증 | VPC > 서브넷 목록에서 `cloud-mission-public-subnet` / `10.0.1.0/24` / `Available` 및 연결 VPC를 확인 |
| 조치 | 중복 서브넷 생성을 취소하고, 이미 생성된 기존 서브넷을 그대로 사용 |
| 결과 | 중복 생성 없이 기존 서브넷을 Public Route Table에 명시적으로 연결 완료. 이후 EC2 생성 및 외부 HTTP 접속 성공 |
| 재발 방지 | 생성 전 서브넷 목록·CIDR 점검. VPC 내 사용 중 CIDR을 다이어그램에 기록하고 새 서브넷 CIDR의 겹침 여부 확인 |

## 사례 2 — SSH 관리 포트 과다 공개 설정 수정 (예방적 조치)

| 단계 | 내용 |
|---|---|
| 증상 | EC2 생성 화면에서 SSH TCP/22 허용 소스가 `0.0.0.0/0`로 설정된 규칙과 개인 IP `121.135.181.35/32` 규칙이 동시에 존재 |
| 가설 | 전체 허용 규칙이 남으면 개인 IP 제한 규칙이 있어도 모든 IPv4에서 SSH 접근이 가능해짐 |
| 검증 | EC2 시작 화면의 인바운드 보안 그룹 규칙 목록과 AWS의 공개 포트 경고 확인 |
| 조치 | SSH `0.0.0.0/0` 규칙 제거. SSH 개인 IP/32 및 HTTP 80 전체 허용 규칙만 유지 |
| 결과 | 수정한 두 규칙으로 EC2 생성. Mac에서 SSH 로그인 성공, 브라우저에서 Nginx 기본 페이지 접속 성공 |
| 재발 방지 | EC2 배포 전 인바운드 규칙 전체 검토: SSH /32, HTTP 80 0.0.0.0/0, 전체 포트 공개 금지 |

## 추가 관찰 (문제 발생 기록과 구분)

- EC2 모니터링 탭에서 `cloudwatch:GetMetricData` 권한 거부가 표시됨. 실습 필수 기능이 아닌 모니터링 조회 권한으로, 권한을 확대하지 않고 진행했음.
- 시스템 로그 탭이 비어 있어 최초 SSH 호스트 키 지문을 콘솔에서 교차검증하지 못했음. 최초 접속 시 SSH의 TOFU(최초 연결 신뢰) 방식으로 호스트 키를 수락했으며, 독립적인 지문 검증을 완료했다고 주장하지 않음.
- EC2 내부 `curl -I http://localhost` 응답: `HTTP/1.1 200 OK`, `Server: nginx/1.30.7`.
- EC2 내부 `curl -I https://example.com` 응답: `HTTP/2 200`.
- 외부 브라우저 `http://3.36.115.9`: Nginx 기본 페이지 표시.

## 제출 증빙 상태

- 콘솔 및 터미널 검증 내역은 대화에서 확인했으나, 저장소의 `docs/screenshots/`에 원본 캡처를 별도로 올려야 완전한 이미지 증빙이 됨.
- IAM 정책의 전체 JSON과 실제 삭제 완료 상태는 아직 확인되지 않았음.
